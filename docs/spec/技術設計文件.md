# OViiAI 平台 技術設計文件

Oct 12, 2026 · @Someone

本文件說明平台「為什麼這樣設計」：元件如何分工、資料如何流動、關鍵決策與取捨、故障時怎麼辦。欄位、端點、建表 SQL 等實作細節以「工程開發手冊」為準。

## 1. 背景與目標

場域有 3 樓層、28 台、三個品牌的巡邏機器人，另有約 100 支 IP 攝影機與既有人臉辨識系統。各廠機器人各有自己的 SDK 與管理系統，控制室無法在一個畫面上統一監控與派工。

**目標**

1. 一個平台監控、派工、遙控全部品牌的機器人，且不綁定單一品牌。
2. 自動派工與充電管理，每層 10 台共用 2 座充電樁。
3. 告警從發生到控制室彈窗 ≤ 3 秒，每筆都有完整處理紀錄。
4. 全部在場內伺服器運作，不依賴外部雲端。
5. 一名工程師即可維運。

**非目標**

- 不自行實作機器人定位、建圖、避障（使用各機器人自帶功能）。
- 不做人臉辨識運算（由既有系統負責）。
- 不取代 NVR 的全天候錄影。
- 本期不做機器人跨樓層、大屏展示、多場域。

## 2. 部署與網路架構

&#91;embedded content: 部署與網路架構 · 4 個網段\]

所有服務跑在一台場內伺服器。對外只有五種連線，其餘都在伺服器內部。

| # | 來源 → 目的 | 協定／埠 | 用途 |
| --- | --- | --- | --- |
| ① | 控制室 → Nginx | HTTPS 443 | 網頁、API、WebSocket |
| ② | 控制室 ↔ MediaMTX | WebRTC：HTTPS 8889 信令＋ UDP 8189 媒體 | 看影像、對講 |
| ③ | MediaMTX → 攝影機 | RTSP 554（伺服器主動拉流） | 攝影機影像 |
| ④ | 轉接器 ↔ 機器人 | 各廠 SDK（宇樹 DDS、萬為依文件）＋ RTSP | 控制、遙測、機器人影像 |
| ⑤ | API ↔ 既有系統 | HTTPS | 人臉事件與名單、上位 Webhook |

轉接器以 host 網路模式執行，直接使用伺服器在機器人網段的網卡（宇樹 DDS 需要同網段廣播）。B2 機身內建開發運算單元，若 Wi-Fi 穿透 DDS 不穩，宇樹轉接器改在機上執行，以 MQTT over TLS（8883）連回伺服器。

## 3. 元件職責

後端是一個模組化單體程式（NestJS），轉接器是獨立的 Python 程序；兩者只透過 MQTT 溝通。

| 元件 | 職責 | 狀態 | 故障影響 |
| --- | --- | --- | --- |
| Nginx | TLS 終結、靜態網頁、反向代理 API 與 WebSocket | 無 | 網頁無法開啟；機器人照常巡邏 |
| Web 前端 | React 單頁應用 | 無 | 同上 |
| API 後端 | 驗證權限、業務邏輯（派工、充電、告警、排程）、指令匯流排、WebSocket 推送 | 無（狀態在 Redis、DB） | 新派工與告警暫停；執行中的導航由機器人自行完成 |
| PostgreSQL ＋ TimescaleDB | 正式資料與遙測時序 | 有 | API 無法寫入，進入唯讀報錯 |
| Redis | 機器人即時狀態、分散鎖、排程佇列、設定變更通知 | 可重建 | 重啟後由遙測在數秒內重建 |
| EMQX（MQTT） | 轉接器與後端之間的訊息匯流排 | 部分（retain） | 平台看不到機器人、無法下指令 |
| MinIO | 平面圖、抓拍、錄影、音檔 | 有 | 無法存取圖片影片 |
| MediaMTX | RTSP 轉 WebRTC、對講音訊轉發 | 無 | 影像中斷；其他功能不受影響 |
| 轉接器（每品牌一個） | 品牌 SDK ↔ 統一格式、座標轉換、心跳 | 無 | 該品牌全部離線；其他品牌不受影響 |
| 模擬器 | 開發與測試用的假機器人，對後端和真轉接器一模一樣 | 無 | 僅開發環境 |

## 4. 關鍵流程

### 4.1 指令（以導航為例）

&#91;embedded content: 指令序列 · 5 個參與者、10 步\]

所有機器人指令都是非同步：API 只負責「送出」，結果以 cmdId 對應、以 WebSocket 推回。這樣瀏覽器不會因為機器人動作慢而卡住。遙控速度是例外：經 WebSocket → MQTT QoS 0，不回 ack。

### 4.2 遙測

1. 轉接器每秒 1–2 次讀機器人狀態，轉成平台座標，發布到 MQTT。
2. 後端寫入 Redis 即時狀態；每 5 秒批次寫入 TimescaleDB（1 Hz）。
3. 後端節流後以 WebSocket 推給訂閱該樓層的瀏覽器。
4. 狀態、電量變化觸發派工、充電排程與告警規則。

### 4.3 P1 緊急任務

1. 告警或使用者建立 P1 任務，跳過審批。
2. 取得該樓層派工鎖；有空閒可用機器人就直接派。
3. 否則選最近一台執行非 P1 任務的機器人：送 stop，原任務轉 paused 並記錄進度。
4. 派出 P1（走 4.1 指令流程）；P1 完成後原任務回佇列，優先派回同一台。

### 4.4 告警

1. 來源（系統規則、機器人事件、人臉系統、環境數值）正規化成統一告警。
2. 去重 → 查等級與通知設定 → 依 AI 信心度決定進「待人工複判」或「未處理」。
3. 寫入資料庫、推 WebSocket；一級告警前端彈窗響鈴。
4. 處理人逐步轉換狀態，每步留歷程；「回報上位」時送出 Webhook。

### 4.5 影像

1. 使用者點攝影機 → 前端向 API 取得 60 秒播放憑證。
2. 瀏覽器以 WHEP 連 MediaMTX；MediaMTX 回後端驗證憑證。
3. MediaMTX 按需向攝影機拉 RTSP，只轉封裝後以 WebRTC 送出；沒人看 10 秒後斷開。

## 5. 關鍵設計決策

每項決策在程式庫 `docs/adr/` 各有一份記錄；後續若推翻，新增一份而不是改舊的。

| # | 決策 | 考慮過的替代方案 | 理由 | 代價 |
| --- | --- | --- | --- | --- |
| D1 | 每品牌一個獨立轉接器，後端只認統一格式 | 後端直接呼叫各家 SDK；使用廠商雲平台 | 品牌差異隔離在一處；一個 SDK 崩潰不拖垮後端；新增品牌不動後端；使用者要求不經廠商平台 | 多一層訊息轉換與部署單元 |
| D2 | 轉接器與後端以 MQTT 溝通 | gRPC、HTTP 輪詢、Redis pub/sub | 一對多訂閱、QoS、Last Will 離線偏測、retain 保留最後狀態；也是機器人業界常見協定 | 多一個服務要維運 |
| D3 | 轉接器用 Python | 全部 TypeScript；C++ | 宇樹、雲深處都有 Python SDK；座標計算有 numpy | 兩種語言；以共用 schema ＋ CI 一致性測試彌補 |
| D4 | 導航、定位、避障用機器人自帶功能 | 平台自寫 SLAM 與路徑規劃 | 廠商已調校過；自寫是數個月的工作量且風險高 | 受限於各廠 SDK 開放程度（B2 導航介面、自動回充待驗證） |
| D5 | 每台機器人以仿射轉換對齊平面圖 | 要求各廠地圖共用原點；平台自建地圖 | 不需改廠商地圖；3 點即可校正、可量化誤差 | 重新建圖後要重校 |
| D6 | 模組化單體後端 | 微服務 | 一名工程師可維運；28 台規模用不到獨立擴展；模組邊界保留日後拆分空間 | 單點；以自動重啟與機器人自主運作彌補 |
| D7 | 遙測存 TimescaleDB（同一個 PostgreSQL） | InfluxDB、只存 Redis | 少一種資料庫；可用 SQL 和任務、告警表 JOIN；內建壓縮與保存政策 | 需用 TimescaleDB 映像 |
| D8 | 機器人即時狀態放 Redis，不每筆寫 DB | 每筆遙測寫 DB | 畫面讀即時狀態的頻率高；DB 只批次寫入 1 Hz 快照 | Redis 重啟會短暫沒有資料（數秒內恢復） |
| D9 | 影像用 MediaMTX 只轉封裝、按需拉流 | 後端自寫轉程；Janus；轉碼成低解析度 | 單一執行檔、CPU 負載低、延遲低 | 攝影機需輸出 H.264；瀏覽器不支援的編碼無法播放 |
| D10 | 派工以「單樓層鎖＋集中式選車」做 | 機器人自行搶單；全域最佳化 | 機器人不跨樓層，各樓層獨立；簡單可預測、容易解釋 | 非全域最佳；10 台規模影響小 |
| D11 | Docker Compose 單機部署 | Kubernetes | 場內一台伺服器；維運門檻低 | 無自動容錯切換；以備份與快速還原彌補 |
| D12 | 人臉系統以「對應層」接入，不複製名單 | 同步名單到平台 | 名單只有一份、個資不重複存放 | 依賴對方系統可用 |

## 6. 容量與效能估算

以 28 台、日後擴充至 50 台為設計上限。以下為推算值，需在 M3 壓力測試驗證。

| 項目 | 推算 | 結果 |
| --- | --- | --- |
| MQTT 遙測流量 | 28 台 × 2 Hz × 約 0.5 KB | 約 56 則／秒、28 KB／秒；EMQX 負載可忽略 |
| 遙測入庫 | 28 台 × 1 Hz × 86,400 秒 | 約 242 萬筆／天；保存 90 天約 2.2 億筆 |
| 遙測儲存 | 未壓縮約 100 B／筆 | 約 0.24 GB／天、90 天約 22 GB；壓縮後預估小於 5 GB |
| WebSocket 推送 | 每台每秒 ≤ 2 則 × 單樓層 10 台 × 20 位使用者 | 約 400 則／秒，Node 單程序可負擔 |
| 影像頻寬 | 1080p H.264 約 4 Mbps × 16 路 | 伺服器進出各約 64 Mbps；千兆網路足夠 |
| 機器人 Wi-Fi 上傳 | 每台被觀看時約 4 Mbps | 同一 AP 下同時觀看多台時需注意，可改用子碼流 |
| 告警影片 | 30 秒 × 4 Mbps ≈ 15 MB × 每天 50 段（假設） | 約 0.75 GB／天、30 天約 22 GB |
| 抓拍 | 300 KB × 每天 500 張（假設） | 約 0.15 GB／天、30 天約 4.5 GB |
| 後端延遲目標 | 遙測→畫面 | ≤ 1 秒（其中節流最多 500 ms） |
| 告警延遲目標 | 事件→彈窗 | ≤ 3 秒 |

結論：系統規模不大，瓶頸在影像頻寬與機器人 Wi-Fi，不在運算。系統規格書建議的 8 TB 影像儲存遠超過需求，可降為 2 TB，或保留空間以拉長保存天數。

## 7. 可靠性與故障處理

設計原則：平台故障時，機器人要「安全停下或繼續手上的事」，絕不能失控；恢復後自動重連、不需人工重設。

| 故障 | 偵測 | 機器人行為 | 平台行為 | 恢復 |
| --- | --- | --- | --- | --- |
| 單台機器人斷線 | 10 秒無遙測或 MQTT Last Will | 繼續或完成當前導航（依廠商） | 標離線、二級告警、任務轉 paused | 轉接器每 5 秒重連；恢復後任務回佇列 |
| 遙控中斷訊 | 500 ms 未收到 teleop | 轉接器送零速度停車 | 遙控頁提示「連線中斷」 | 重新取得遙控鎖 |
| 轉接器程序崩潰 | 心跳停止 15 秒 | 同斷線 | 該品牌全部標離線，一級系統告警 | Docker 自動重啟 |
| EMQX 停止 | 後端與轉接器連線中斷 | 同斷線 | 全部離線、頁面頂部顯示異常 | 自動重啟；雙方自動重連 |
| API 後端停止 | Docker healthcheck | 執行中導航由機器人完成 | 無法操作；排程暫停 | 自動重啟；排程由 BullMQ 補跑遲到 30 分鐘內的工作 |
| PostgreSQL 停止 | 連線失敗 | 不受影響 | 唯讀；遙測批次在記憶體暫存最多 5 分鐘 | 自動重啟；硬碟故障則從每日備份還原 |
| Redis 重啟 | 連線中斷 | 不受影響 | 即時狀態短暫空白 | 遙測數秒內重建；鎖自動過期 |
| 整台伺服器停電 | — | 繼續當前任務，低電量時由機器人自帶回充（若有） | — | 開機後全部服務自動啟動；建議伺服器接 UPS |
| 指令無回覆 | 15 秒未收到 accepted | — | 指令失敗、三級告警、任務 failed | 使用者重試或改派 |
| 急停 | 遙測 state=estop | 立即停止 | 任務 paused、告警 | 有權限者解除；實體急停需現場解除 |

嚴格要求：急停指令不經佇列、不受任何鎖；任何需要權限的檢查失敗都不能擋住急停以外的「停止」類指令。

## 8. 安全設計

| 層面 | 設計 |
| --- | --- |
| 網路分段 | 控制室、伺服器、機器人 Wi-Fi、攝影機分屬不同網段；機器人與攝影機網段只允許伺服器連入，控制室不能直連機器人 |
| 傳輸 | 瀏覽器一律 HTTPS；WebRTC 內建 DTLS 加密；MQTT 只在伺服器內部網路，若轉接器改在機上執行則開 TLS 8883 |
| 驗證 | 獨立帳密；argon2id 雜湊；5 次失敗鎖 15 分鐘；accessToken 15 分鐘、refresh token 7 天且可撤銷 |
| 授權 | 角色權限碼，每個 API 端點與 WebSocket 指令都在後端檢查；前端隱藏僅為便利 |
| 影像權限 | MediaMTX 每次播放都回後端驗證 60 秒短期憑證 |
| 系統間驗證 | 轉接器各自 MQTT 帳密＋ACL；人臉系統推送用 API 金鑰＋IP 白名單；上位 Webhook 以 HMAC 簽章 |
| 秘密管理 | 密碼與金鑰只在 `.env`；RTSP 帳密、機器人連線密鑰在 DB 以 pgcrypto 加密 |
| 稽核 | 所有重要操作寫入 op\_logs，應用層不提供刪改 |
| 個資 | 不儲存人臉特徵與名單照片；告警截圖依保存政策到期刪除 |
| 防濫用 | 登入與指令 API 限流；上傳檔案限制類型與大小 |
| 更新 | 每月檢查相依套件安全公告（GitHub Dependabot） |

## 9. 可觀測性

- **日誌**：後端與轉接器輸出 JSON 日誌，每筆帶 `robotId`、`taskId`、`cmdId`，可用同一個 cmdId 串起瀏覽器→後端→轉接器→機器人的完整過程。
- **健康檢查**：`/health` 回報資料庫、Redis、MQTT、MinIO、MediaMTX 與各轉接器心跳；異常時產生系統告警，控制室當場看得到。
- **指標（建議，第二期可加 Prometheus＋Grafana）**：遙測延遲、指令成功率與耗時、各樓層在勤台數、充電排隊長度、告警未處理數、WebSocket 連線數、影像同時觀看數。
- **業務統計**：機器人可用率由 `robot_state_log` 計算，每日彙總，提供第二期報表使用。

## 10. 擴充性

| 變化 | 需要做的事 | 不需要動的地方 |
| --- | --- | --- |
| 新增一個機器人品牌 | 寫一個轉接器＋ MAPPING.md；在機器人管理頁新增品牌選項 | 後端業務邏輯、前端頁面 |
| 增加機器人台數 | 機器人管理頁新增、座標校正 | 程式；50 台以內無需調整硬體 |
| 新增樓層 | 地圖管理頁新增樓層、上傳平面圖 | 程式 |
| 新特殊能力（升降桿、新感測器） | 能力清單加一項；指令與前端依能力顯示按鈕 | 其他品牌 |
| 機器人跨樓層（搭電梯） | 任務加「樓層切換」步驟、選車改為跨樓層、座標校正改為每台多張地圖 | 轉接器介面已帶 floor 欄位 |
| 上位系統、其他外部系統 | 在 integrations 加一個對應層 | 告警管線 |
| 多場域 | 各場域各部署一套；若需總部總覽，另建彙整服務 | 單場域架構 |

## 11. 風險與待決事項

| 項目 | 影響的設計 | 目前做法 |
| --- | --- | --- |
| B2、X30 是否支援自動對接充電；B2 導航介面 | D4；充電排程 | 不支援時，充電排程改為低電量提醒人工充電或換電池 |
| 萬為 SDK 內容 | 萬為轉接器 | 文件到手後一週內完成對照表 |
| 攝影機編碼是否為 H.264 | D9 | 若有 H.265，改用子碼流或對該路啟用轉碼 |
| 各機型是否支援即時音訊與跟隨 | 對講、跟隨功能 | 對講先做方案 A、備方案 B；跟隨以能力清單控制顯示 |
| 人臉系統支援推送或只能輪詢 | D12 | 兩種都設計，依對方文件啟用 |
| 各樓層 Wi-Fi 覆蓋（尤其 B1） | 可靠性 | 測試人員繪製訊號地圖；弱訊區設為特殊區域（減速、不停留） |
| 每層僅 2 座充電樁 | 充電排程 | 排隊機制已設計；若實測在勤台數不足再評估增樁 |
| 單台伺服器單點 | D6、D11 | UPS＋每日備份；機器人在平台故障時仍可自主運作 |
