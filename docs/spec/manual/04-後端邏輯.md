# 後端業務邏輯

本分頁定義後端各模組的行為與演算法。所有門檻值從 `settings` 讀（快取在記憶體，設定變更時由 Redis pub/sub 通知刷新）。

## 1. 機器人即時狀態（fleet）

1. 訂閱 `rms/robot/+/telemetry`，經 zod 驗證後寫入 Redis hash `robot:{code}`（最新狀態＋`lastSeen`）。
2. 每台每秒最多取一筆批次寫入 `telemetry`（每 5 秒 flush 一次）。
3. `state` 與上一筆不同時寫 `robot_state_log`，並發 `robot.state` 給 WebSocket（每台節流 500 ms）。
4. 每秒檢查 `lastSeen`：超過 `robot.offlineSec` → 標離線、發系統告警、其任務進入 `paused`。
5. 故障碼等級 1 → 系統告警；電量低於回充門檻 → 交給充電排程（§3）。

**指令匯流排（CommandBus）**

- `send(robotCode, type, args)` 產生 `cmdId`，發布到 `cmd` 主題，在 Redis 記錄待回覆指令。
- 收到 `ack` 更新狀態並推 `robot.cmdResult`；超過 `cmd.timeoutSec` 未收到 `accepted` → 失敗，發系統告警「指令失敗」。
- 急停指令不排隊、不受任何鎖限制，且同時寫入操作日誌。

**遙控鎖**：`teleop:{code}` 存 `{userId, lockId}`，TTL 30 秒、每次收到 teleop 續期。取得鎖時先對機器人送 `pause`，任務轉 `paused`；釋放後送 `resume`。另一人取鎖回 409 `TELEOP_LOCKED`（系統管理員可強制接管）。

## 2. 派工（dispatch）

### 任務狀態轉換

| 從 | 到 | 觸發 |
| --- | --- | --- |
| （新建） | pending\_approval | 非 P1，且審批開啟（`dispatch.approval` 為 true 且今天 ≤ `approvalUntil`），且來源不是已核准的排程 |
| （新建） | queued | 其他情況 |
| pending\_approval | queued ／ rejected | 核准／駁回 |
| queued | assigned | 選車成功，已送 navigate／patrol 指令 |
| assigned | running | 收到 `accepted` |
| running | done ／ failed | `goal_reached`（巡邏為最後一點）／`goal_failed` 或指令失敗 |
| running | paused | 被 P1 中斷、遙控接管、機器人離線、急停、回充 |
| paused | queued | 中斷原因解除（從 `progress` 續做） |
| 任何未結束 | cancelled | 使用者取消 |

每次轉換寫 `task_events` 並推 `task.updated`。

### 選車演算法

觸發時機：任務進入 queued、機器人變 idle、充電完成、每 10 秒保底掃一次。同樓層的選車以 Redis 鎖 `dispatch:{floor}` 串行處理，避免一台機器人被派兩次。

```ts
function pickRobot(task: Task, robots: RobotLive[], s: Settings): RobotLive | null {
  if (task.pinnedRobot) return robots.find(r => r.id === task.robotId && eligible(r, task, s)) ?? null;
  const cands = robots.filter(r => eligible(r, task, s));
  if (!cands.length) return null;
  const target = targetPoint(task);              // 興趣點或路徑起點
  return minBy(cands, r => dist(r.pose, target) - r.battery * 0.01); // 距離為主，同距離選電量高
}

function eligible(r, task, s) {
  return r.floor === task.floorId && r.online && r.enabled
    && r.state === 'idle' && !r.teleopLocked
    && r.battery >= s.charge.minAccept
    && capsCover(r.caps, task.requiredCaps);
}
```

第一期距離用直線距離；第二期若機器人 SDK 可回路徑長度再替換。佇列順序：優先級 P1 > P2 > P3 > P4，同級先建先做。

### P1 插隊

1. 有 eligible 的空閒機器人 → 直接派。
2. 否則若 `dispatch.p1Preempt`：在同樓層「執行非 P1 任務、電量 ≥ minAccept」的機器人中選最近者；對它送 `stop`，原任務轉 `paused` 並記 `preempted_by`，再派 P1。
3. P1 完成後，被中斷任務回 `queued`，優先派回同一台。
4. 仍然沒有車 → P1 留在佇列最前，並發一級告警「P1 任務無可用機器人」。

## 3. 充電排程（charging）

- **觸發**：電量 ≤ `returnAt`（預設 25%）且未在充電；或使用者按「回充」。執行中的任務轉 `paused`。
- **分配**：同樓層、同品牌、未佔用的樁中選最近者；以 Redis 鎖確保同一樁不被兩台搭。
- **排隊**：樁都佔滿時進入 `charge:queue:{floor}`（依電量由低到高）；機器人先導航到樁旁等候點。電量低於 10% 且排在第二以後 → 二級告警。
- **結束**：充到 `resumeAt`（預設 90%）且有人排隊 → 離樁讓位；無人排隊則留在樁上充到 100%，狀態仍視為可接任務（接任務時自動離樁）。
- 樁佔用、排隊變化推 `charger.updated`。每次充電紀錄開始、結束電量，供第二期能耗頁使用。

**人工充電模式**：給不支援自動對接充電的機型（B2、X30 待確認）。以 `charge.mode.{brand}` = `auto` 或 `manual` 設定。manual 時，電量低於回充門檻就派機器人回到指定充電點、發「需人工充電或換電池」二級告警給維修人員；人員在畫面按「完成充電」後恢復上線。換電池機型以電量跳升自動判斷完成。

## 4. 巡邏排程（patrol）

- 每筆 `patrol_schedules` 對應一個 BullMQ repeatable job（cron 由 `start_time`＋`repeat` 換算，Asia/Taipei）。排程新增／修改／停用時同步更新 job。
- 觸發時建立 `source=schedule` 的任務。排程本身在建立時已經審批，觸發的任務不再審批。
- 指定機器人但它急停、離線或電量不足 → 任務留在佇列最多 30 分鐘，並發三級告警說明延後原因；逾時則 failed。
- 路徑被排程引用時不可刪除。

## 5. 告警管線（alarms）

```text
來源（系統規則／機器人事件／人臉系統／環境數值）
  → 正規化成 {type, robotId?, cameraId?, floorId, x, y, message, confidence?, media?}
  → 去重：同 type＋同來源在 dedup_sec 內 → repeat_count+1，不新增
  → 查 alarm_rules 取得等級與通知設定
  → 初始狀態：confidence < aiConfidence → review；need_handle → open；否則 info
  → 寫入 alarms ＋ alarm_events
  → 推 alarm.new；第二期依設定發簡訊
```

**合法狀態轉換**（`POST /alarms/:id/transition`，其他一律 409）

| 從 | 可到 |
| --- | --- |
| review | open（確認屬實）、false\_alarm |
| open | handling、false\_alarm |
| handling | closed、reported、false\_alarm |
| reported | closed |

**系統告警規則（第一期）**

| type | 條件 | 預設等級 |
| --- | --- | --- |
| battery\_low | 電量 ≤ returnAt | 2 |
| offline | 超過 offlineSec 無遙測 | 2 |
| estop | 機器人進入急停 | 2 |
| fault | 故障碼等級 1 | 2 |
| weak\_signal | rssi < -75 dBm 持續 30 秒 | 3 |
| stream\_down | 影像閘道回報串流中斷 > 15 秒 | 2 |
| cmd\_failed | 指令逾時或失敗 | 3 |
| p1\_preempt ／ p1\_no\_robot | 插隊發生／無可用機器人 | 3 ／ 1 |
| charge\_queue | 低電量排隊過久 | 2 |

## 6. 權限

權限碼定義在 `packages/shared/src/perms.ts`，與原型一致：

- 頁面：monitor, robots, remote, nav, energy, reports, history, stats, runlog, dispatch, face, env, points, media, sysalarm, bizalarm, alarmset, captures, records, settings, params, robotmgr, maps, users, roles, oplog, logs, versions, help
- 操作：op.remote, op.estop, op.dispatch, op.approve, op.alarm, op.config

後端以 `@RequirePerm('op.estop')` 裝飾器＋Guard 檢查；前端依 `/me` 的權限隱藏選單與按鈕，但以後端檢查為準。初始角色：系統管理員、警衛、維修人員、主管，權限內容見系統規格書第 3 節。

## 7. 操作日誌

以 `@OpLog('robot.estop', (req) => req.params.id)` 裝飾器＋攔截器自動記錄：人、時間、IP、動作、對象、參數摘要、成功與否。必須記錄的動作：登入登出、所有機器人指令、遙控接管／歸還、建單／審批／取消、告警狀態變更、所有設定與帳號權限變更。
